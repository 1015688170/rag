# RAG 系统流程说明

## 1. 文档目的

本文档用于说明当前 RAG（Retrieval-Augmented Generation，检索增强生成）系统的整体处理流程、模块职责和业务价值。当前版本已经支持知识文件上传、文档切片入库、混合检索、重排、基于来源生成答案，以及基础权限控制。

## 2. 系统定位

本系统是一套面向企业内部运维知识库的问答测试台。它不是让大模型直接凭通用知识回答问题，而是先从企业知识库中检索相关资料，再由大模型基于资料生成答案。

系统主要服务以下场景：

- 运维新人不熟悉标准术语，只能用白话描述问题。
- 实习生需要快速理解告警、日志、命令和 SOP。
- 一线值班同学需要查询可执行步骤、配置示例和排障依据。
- 管理或验收人员需要看到答案来源，确认回答是否有据可查。
- 知识库维护人员需要把 Markdown、TXT、PDF、DOCX、JSON 等文件上传并索引到检索库。

## 3. 总体架构

系统采用前后端分离架构：

- 前端：基于 React + Vite，负责用户提问、参数配置、提示词调整、文档上传管理、权限配置、答案和来源展示。
- 后端：基于 FastAPI，负责执行完整的 RAG 流程、文档入库流程和权限过滤。
- 元数据层：基于 SQLite，保存上传文档、入库任务、文件哈希、切片数量、权限字段和处理状态。
- 检索层：基于 Azure AI Search，保存知识切片、向量、来源元数据和权限元数据，并执行关键词检索与向量检索。
- 重排层：基于本地 BGE Reranker，对召回片段做相关性排序。
- 生成层：支持 GPT-4o 与 Claude Opus 4.5 等大模型生成最终回答。

整体链路可以概括为：

文件上传 -> 文本解析 -> 文档切片 -> 向量化 -> 写入 Azure AI Search -> 用户提问 -> 权限过滤检索 -> 本地重排 -> 大模型生成 -> 答案与来源返回

## 4. 知识文档上传与入库流程

当前版本提供文档管理页面，用户可以选择目标 Azure AI Search 索引后上传企业知识文件。后端会同步完成解析、切片、向量化和索引写入。

支持的文件类型：

- `.md`
- `.txt`
- `.pdf`
- `.docx`
- `.json`

上传处理步骤：

1. 校验文件后缀和文件大小，单文件上限为 20MB。
2. 将原始文件保存到 `backend/storage/uploads/`。
3. 计算文件 `sha256`，作为 `file_hash`。
4. 如果相同 `file_hash` 的文档已经成功入库，则返回 `already_exists`，避免重复写入 Azure AI Search。
5. 按文件类型解析文本，生成 `DocumentSection`。
6. 将超长 section 切成 `DocumentChunk`。
7. 对每个 chunk 生成 embedding。
8. 将 chunk、向量、来源信息和权限元数据写入 Azure AI Search。
9. 更新 SQLite 中的文档状态、任务状态和切片数量。

## 5. 文档切片策略

当前版本采用两阶段切片：

1. 先按文件类型解析为 `DocumentSection`。
2. 再只对超过阈值的 section 拆成 `DocumentChunk`。

默认参数：

- `chunk_size=1000` 字符。
- `chunk_overlap=150` 字符。
- 当前按字符数切分，不按 token 切分。
- 只有 section 超过 `chunk_size` 时才使用 overlap。
- 空 chunk 会被跳过。

不同文件类型的解析方式：

- Markdown：按 `#` 到 `######` 标题分 section，`section_path` 保存标题层级。
- TXT：按空行分段落，再合并短段落直到接近 `chunk_size`。
- DOCX：使用 `python-docx` 读取；Heading 样式作为 section 标题；没有 Heading 时按普通段落处理。
- PDF：使用 `pypdf` 逐页抽取文本，按段落合并，并保留 `page_start` 和 `page_end`；扫描版 PDF 暂不支持 OCR。
- JSON：使用 Python 标准 `json` 解析，按 JSON path 递归拆分，较小字段会保留在父级 section 中。

## 6. 基础权限控制

当前权限控制覆盖文档元数据、Azure AI Search 切片元数据和问答检索阶段。

权限字段包括：

- `visibility`：文档可见性，支持 `public`、`private`、`restricted`。
- `owner_id`：文档所有者。
- `allowed_departments`：允许访问的部门列表。
- `allowed_roles`：允许访问的角色列表。

权限处理方式：

1. 上传时，前端可提交可见性、所有者、允许部门和允许角色。
2. 后端将权限字段保存到 SQLite 的文档记录。
3. 后端将同样的权限字段写入每个 Azure AI Search chunk。
4. 聊天检索时，后端根据当前用户身份生成 Azure AI Search filter。
5. 权限过滤在 Azure AI Search 召回阶段执行，而不是召回后再由 Python 过滤。
6. 未携带身份信息的请求只能检索 `public` 文档。
7. 删除文档仅允许文档所有者或 `admin` 角色执行。

该设计保证权限与知识切片一起进入检索索引，避免无权限内容进入后续重排和大模型上下文。

## 7. 面向新人白话问题的提示词策略

运维新人和实习生提问时，常见表达往往不够标准。例如：

- "pod 炸了咋看？"
- "CPU 很高怎么查？"
- "流水线挂了，提示 exit code 1 是啥？"
- "Grafana 上想看生产环境容器 CPU，怎么写 PromQL？"

这些问题可能缺少完整工程术语。为提高回答质量，系统提示词要求大模型先做问题理解与关键词标签化，再回答问题。

### 7.1 标签体系

系统会将用户问题拆解为以下标签：

- 场景：例如 Kubernetes、GitLab CI、Grafana、Prometheus、镜像扫描、发布变更。
- 对象：例如 Pod、容器、节点、Pipeline、镜像、服务、命名空间。
- 症状：例如 OOM、CPU 高、水位高、Exit Code 1、启动失败、漏洞阻断。
- 指标/命令：例如 PromQL、kubectl、journalctl、rate、container_cpu_usage_seconds_total。
- 意图：例如排查原因、确认依据、生成查询语句、给出 SOP、解释告警。

如果用户没有明确表达某类信息，系统会标记为“未明确”，避免自行脑补。

## 8. RAG 问答处理流程

用户在前端输入问题后，系统按以下步骤执行：

1. 前端将用户问题、用户身份、Embedding 模型、聊天模型、召回数量、重排数量、提示词模板等参数提交到后端。
2. 后端根据所选 Embedding 模型，将用户问题转换为向量表示。
3. 后端根据用户身份和权限字段生成检索过滤条件。
4. 后端将原始问题文本、问题向量和权限 filter 一起提交给 Azure AI Search，执行混合检索。
5. Azure AI Search 只返回当前用户有权访问的候选知识片段。
6. 后端将候选片段交给本地 BGE Reranker，按问题相关性重新排序。
7. 后端选取重排后的前 N 条片段，拼接成大模型参考资料。
8. 后端将系统提示词、参考资料和用户问题提交给选定的大模型。
9. 大模型基于参考资料生成结构化回答。
10. 后端返回答案、来源片段、模型信息和分数信息。
11. 前端展示答案和参考数据源，方便用户核对依据。

## 9. 关键阶段说明

### 9.1 向量化

系统将用户问题和上传文档 chunk 转换为向量，用于语义检索。向量化可以帮助系统找到“意思相近但文字不完全相同”的知识内容。

当前支持：

- `ada-002`
- `google-005`

### 9.2 混合检索

系统使用 Azure AI Search 执行混合检索：

- 关键词检索：适合命中明确术语、命令、报错码、指标名。
- 向量检索：适合处理白话问题和语义相近表达。
- 权限过滤：适合在召回阶段排除用户无权访问的文档片段。

混合检索同时兼顾字面命中、语义理解和访问控制，适合企业内部知识库场景。

### 9.3 本地重排

召回结果可能包含多条片段，其中有些只是弱相关。系统使用 BGE Reranker 对“问题 + 片段”重新打分，挑出最适合送入大模型的内容。

重排的作用：

- 提高参考资料相关性。
- 减少无关片段干扰。
- 提升最终回答准确性。

### 9.4 答案生成

大模型不会直接自由发挥，而是基于系统提供的参考资料回答。当前提示词要求回答优先采用以下结构：

## 问题标签

展示场景、对象、症状、指标/命令和意图。

## 结论

先给新人能看懂的直接结论。

## 操作步骤

给出可执行的排查步骤、命令或查询语句。

## 注意事项

说明风险、边界和容易误解的地方。

## 参考来源

列出答案依据来自哪些知识片段或文件。

### 9.5 来源返回

系统会将最终使用的参考片段返回给前端，包括：

- 来源文件路径。
- 片段预览。
- 召回分数。
- 重排分数。
- 分数来源。

这使得使用方可以核验答案依据，降低“模型编造”的风险。

## 10. 异常与兜底

### 10.1 上传入库失败

如果文件类型不支持、文件超过大小限制、JSON 解析失败、PDF 无法抽取文本、embedding 生成失败或 Azure AI Search 写入失败，后端会将文档和任务状态标记为 `failed`，并记录错误信息。

### 10.2 未检索到有效资料

如果知识库中没有足够依据，系统不会强行生成答案，而是提示资料不足，并说明缺少哪类资料。

### 10.3 重排不可用

如果本地重排模块因依赖、模型文件或运行环境问题异常，系统会自动降级为直接使用召回结果继续回答。

此时前端会显示：

- `score_source = recall`
- `rerank_score` 为空
- 页面提示“重排不可用”

该机制保证系统在局部模块异常时仍具备基本问答能力。

## 11. 系统价值

从业务角度看，本系统具备以下价值：

- 降低新人使用门槛：允许用户用白话描述问题。
- 提升知识利用率：把内部文档、规范和 SOP 转成可问答能力。
- 降低知识维护成本：支持通过前端上传文件并自动切片入库。
- 增强答案可信度：答案附带来源，便于审阅和验收。
- 支持基础权限隔离：无权限文档不会进入召回、重排和大模型上下文。
- 提升排障效率：将检索、筛选、整理步骤自动化。
- 支持持续优化：提示词、模型、召回数量、重排数量和知识索引均可调整。

## 12. 总结

本系统的核心不是让大模型直接回答，而是围绕企业知识库建立“文档上传 -> 文本切片 -> 向量入库 -> 白话问题理解 -> 权限过滤检索 -> 结果重排 -> 基于依据生成答案”的闭环。

该流程既能照顾运维新人和实习生的自然表达习惯，又能保证回答尽量有依据、可追溯、可解释，并通过基础权限控制降低企业内部知识泄露风险，适合作为企业内部运维知识问答和 RAG 效果验证平台。
